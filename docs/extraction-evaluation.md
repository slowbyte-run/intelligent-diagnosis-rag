# 抽取评估：脱离图谱与检索，直接看断言

对应 issue #33。抽取评估只做一件事：把一批**冻结的真实证据段**交给现有抽取路径，比对产出与人工标注，给出**断言级召回率与精度**。它不读图谱、不跑检索、不写任何数据。

两套评估的基线并排、可比性规则与标注口径 caveat，见
[`docs/eval-baselines.md`](eval-baselines.md)。

这解决的是 `docs/extraction-variance.md` 里那个问题：以前「改了提示词有没有变好」只能看检索命中率，而检索分数同时受抽取抽样和检索策略影响，无法归因。现在抽取侧有了独立判据，且默认重复 3 次报告分布而不是单点（见第六节）；**单次运行仍然只是一次抽样**，不要单独引用。

## 一、标注集

资产在 `src/rotating/idr_rotating/extraction_annotations.json`，与本体、金标准集同级。

- **21 段证据段，来自 6 篇真实语料**：3 篇中文专利（`c169b3184c37a610`、`ddaef5ea68310f1b`、`66f9a7c0b49899ca`）共 11 段，3 篇英文论文（`742178038a41d5ea`、`1be1ecd65c1482c8`、`4f88106f26629c63`）共 10 段。
- 证据段原文与 ID 直接取自已入库图谱（`Evidence` 节点），**没有重新解析 PDF**。ID 形如 `ev:<16 位文献标识>:<页>:<字符区间>`，加载时会校验页、文本长度与字符区间一致。
- 覆盖六种实体类型（`equipment_class`、`component`、`fault_mode`、`fault_cause`、`symptom`、`detection_method`）与五种主要关系（`has_component`、`has_fault_mode`、`has_cause`、`indicated_by`、`detected_by`）。`confused_with` 未被覆盖：语料里没有足够明确的「两种故障易混淆」陈述，硬标会变成编造。

格式：

```json
{
  "schema_version": 1,
  "segments": [
    {"id": "ev:c169b3184c37a610:3:1374-1434", "page": 3, "text": "..."}
  ],
  "expected_entities": [
    {"evidence_id": "ev:c169b3184c37a610:3:1374-1434", "name": "断齿", "type": "fault_mode"}
  ],
  "expected_relations": [
    {"evidence_id": "ev:c169b3184c37a610:3:1374-1434",
     "head": "齿轮副", "type": "has_fault_mode", "tail": "断齿"}
  ]
}
```

加载期会失败的情况（`load_annotations`）：

- 引用不存在的证据段；
- 未知实体/关系类型、内部类型（如 `evidence`）；
- 标注写成别名而不是规范名（流水线会把别名归一成规范名，写成别名必然错分）；
- 关系端点没有在同一段里标注为实体、或违反本体的 domain/range；
- 证据段文本长度与字符区间不符、段落没有任何期望断言、同段重复断言。

## 二、判定规则

评分按**文献**分组：抽取本来就是逐篇调用模型，跨文献的同名概念不能互相顶替。每篇内，期望断言与输出断言先按规范化名称去重（`normalize_term`：全半角、大小写、空白），然后：

| 情况 | 计数 |
|---|---|
| 期望 `(name, type)` 出现在输出 | 命中（召回分子） |
| 输出断言与标注完全一致 | 命中（精度分子） |
| 期望实体没出现、也没有同名实体 | 漏抽 |
| 同名实体出现但类型不同 | 类型不符 |
| 期望关系没出现，但存在同类型且头端或尾端相同的输出 | 端点不符 |
| 期望关系完全没出现 | 漏抽 |
| 输出里有、标注里没有的断言 | 精度损失（分母增加） |

- **召回率** = 命中数 / 去重后的期望断言数。
- **精度** = 命中数 / 去重后的输出断言数。
- 三类未命中（漏抽、类型不符、端点不符）分开计数，互斥；输出多出的断言另算精度损失，可与未命中同时发生。

关系类型不符在实际抽取路径上大多会被本体校验拦下（进待审队列），因此计数通常为 0；判定逻辑仍保留，未来本体允许多个关系共用同组 domain/range 时即可生效。

## 三、命令

```bash
export UV_CACHE_DIR=$PWD/.uv-cache
set -a; . .env; set +a
uv run idr extract-eval --runs 3 --out data/output/reports/extract-eval.json
```

- `--annotations PATH` 换一份标注集；
- `--limit N` 只评按标注顺序的前 N 篇文献，控制真实调用成本；
- `--runs N` 重复运行次数，默认 3，最少 2。每次运行都要对每篇文献调用一次模型，成本按「文献数 × 运行次数」计；
- `--out PATH` 落盘 JSON（`schema_version: 2`，含每次运行明细与 `distribution`）。

## 四、单次运行的历史基线（2026-11-13）

这一节保留 issue #33 交付时的单次运行数字，用于历史对照。**它是一次抽样**；同一份标注集上稍后做的三次重复运行给出了更高的召回与精度，见第六节。

## 五、这份标注集最弱的地方

1. **英文文献的命名口径**。抽取输出会做本体归一（`ball bearing` → 滚动轴承、`chipped tooth` → 断齿、`thermal unbalance` → 转子不平衡、`synchronous amplitude` → 1×转频振动突出），而标注按英文原文术语写的是自由词。这部分在评分里同时表现为「漏抽」与「精度损失」，主要压低了三篇英文文献的分数，不全是抽取能力问题。下一步要么给期望断言加「可接受的规范名」一栏，要么英文文献直接按本体规范名标注。
2. **泛化自由词很少被抽出**。`振动信号`、`齿轮故障`、`加速度传感器`、`测振传感器` 这类没有本体实例的概念，模型基本不产出；它们拉低召回，是提示词与本体引导方向的真实反映，但也说明这份标注对「原文术语」的要求比流水线当前契约更严。
3. **同一篇内跨段的端点不符**。评分按文献聚合，`齿轮副 -[has_fault_mode]-> 齿轮故障` 会被判成对另一段产出的 `齿轮副 -[has_fault_mode]-> 齿面磨粒磨损` 的端点不符。断言本身没被抽到是确定的，但「端点不符」这个归因在跨段时并不精确。
4. **`66f9a7c0b49899ca` 的第 2 段（`1:1327-1653`）过密**。一段里标了 14 个实体、6 条关系；其中「轴弯曲 / 不对中 / 共振 / 不平衡」在专利里是「故障原因」，但本体把这些建模成 `fault_mode`，而 `has_cause` 只允许 `fault_mode -> fault_cause`，所以四条「原因是 X」无法表达，只能标注 `indicated_by` / `detected_by`。这暴露的是本体建模缺口，不是标注笔误。
5. **双栏英文版面**。`4f88106f26629c63` 的段落被 PDF 解析切成两栏交错的碎片，部分实体只在半句里出现；保留它是有意覆盖「真实版面质量差」的情况，但期望断言因此偏保守。

## 六、重复运行与分布（#34）

单点数字不是能力估计，所以 `idr extract-eval` 现在默认重复 3 次，报告每次运行、两两重合度与极差。

### 实现

评分没变：`extract_annotated()` 仍是一次逐篇运行，`score_extractions()` 仍是纯函数。重复层在 `extraction_distribution.py`：

- `measure_extraction_distribution()` 在 `extract_annotated()` 外面循环 N 次，每次把逐篇输出交给 `score_extractions()`；
- 每次运行记录召回率、精度，以及**这次命中了哪些标注断言**的集合（键含证据段 ID，不同段里的同名断言不会互相顶替）；
- 两两重合度用 Jaccard，复用 `variance.py` 的 `pairwise_overlap`；极差复用 `MetricSpread`（最大值 − 最小值）。指标有缺失值时（例如某次没有任何输出，精度没有分母）极差为 `None`，不拿 0 冒充；
- 报告同时给出「每次都命中」「至少一次命中」「只在部分运行命中」的断言数；JSON 里每次运行都保留逐篇明细、逐断言状态与多出的断言。

### 2026-11-13 的 N=3 实测

模型 `deepseek-v4.1-flash`，标注集 6 篇文献、21 段证据段、去重后 159 条期望断言；6 篇 × 3 次 = 18 次模型调用。

| 运行 | 期望 | 输出 | 命中 | 召回率 | 精度 | 漏抽 | 类型不符 | 端点不符 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| #1 | 159 | 90 | 25 | 15.7% | 27.8% | 123 | 1 | 10 |
| #2 | 159 | 104 | 25 | 15.7% | 24.0% | 122 | 1 | 11 |
| #3 | 159 | 100 | 24 | 15.1% | 24.0% | 123 | 1 | 11 |

| 指标 | 最低 | 最高 | 极差 |
|---|---:|---:|---:|
| 召回率 | 15.1% | 15.7% | 0.6 个百分点 |
| 精度 | 24.0% | 27.8% | 3.8 个百分点 |

命中集合的重合与稳定性：

| 项 | 数值 |
|---|---|
| 两两 Jaccard（#1-#2 / #1-#3 / #2-#3） | 1.000 / 0.960 / 0.960 |
| 两两 Jaccard 均值 | 0.973 |
| 每次运行都命中 | 24 / 159（15.1%） |
| 至少一次命中 | 25 / 159（15.7%） |
| 只在部分运行命中（抖动） | 1 条：`ev:66f9a7c0b49899ca:1:1327-1653` 的「转子（component）」，#1/#2 命中、#3 漏抽 |
| 三次的命中集合完全一致 | 否 |

### 这三次运行差多少，说明了什么

1. **命中集合几乎不抖，多出的断言在抖。** 三次两两重合 0.96–1.00，159 条期望断言里只有 1 条在三次之间进出；但输出断言总数是 90 / 104 / 100。召回率只动 0.6 个百分点，精度动 3.8 个百分点——差异主要来自「多抽了什么」，不是「漏了哪些标注」。
2. **本次运行内的窄带不是置信区间。** issue #33 的单次基线是 12.6% / 22.0%（命中 20 条），落在今天三次运行区间（15.1%–15.7% / 24.0%–27.8%）**之外**；同一份标注集、同一模型，T3 的提交在 06:28，这三次运行在 06:40。也就是说，跨批次/跨时间的波动（至少 2.5 个百分点召回）比这一批三次运行的极差（0.6 个百分点）更大。3 次重复能摊开抽样噪声，但不能证明这就是模型能力的全部波动范围。（仓库记录只能证明标注集与评分口径没变，不能证明 T3 基线一定跑在最终提交的那个代码版本上；但两批之间的差已经大于批内极差。）
   后来的复跑修正了「0.6 个百分点」这个量级：同一提交上再跑一批 N=3，批内召回极差就有 6.9 个百分点，见下一节。
3. **T3 基线（12.6% / 22.0%）的可信度：方向对，小数点不可信。** 它是一次抽样，今天没有被复现（命中 20 对 24–25）；把复跑也算进去，目前所有观测落在召回 12.6%–20.1%、精度 21.4%–33.7% 的范围内。用它和改动后的单次运行比「提高了几个百分点」会把抽样噪声当成效果；至少要求两条分布区间不重叠，或者在不同时间各跑一组再比。
4. **判断改动时看哪个数。** 召回看「至少一次命中 / 每次都命中」的差（抖动断言），精度看输出断言数的变化；单看其中一次运行的精度会被多出的断言带偏。两次运行之间真正的差别如果只有一两条断言，这个方法还分辨不出来——这也说明标注集 159 条断言、实际只命中二十几条时，精度对个别多抽很敏感。

### 2026-11-13 06:57 的复跑：批内极差也可以很大

写 `docs/eval-baselines.md` 时在同一提交（0fd9d0d）上复跑了同一批 N=3。抽取相关文件自
#34 以来没有任何改动（`git diff d5df6f1..HEAD` 为空），模型仍是 `deepseek-v4.1-flash`。

| 运行 | 输出 | 命中 | 召回率 | 精度 |
|---|---:|---:|---:|---:|
| #1 | 98 | 21 | 13.2% | 21.4% |
| #2 | 108 | 26 | 16.4% | 24.1% |
| #3 | 95 | 32 | 20.1% | 33.7% |

召回率 13.2%–20.1%（极差 **6.9 个百分点**），精度 21.4%–33.7%（极差 **12.3 个百分点**）；
两两 Jaccard 0.808 / 0.656 / 0.706，均值 0.723；每次运行都命中 21/159，至少一次命中
34/159，只在部分运行命中 13 条。复跑报告留在
`data/output/reports/extract-eval-runs-3-recheck-20261113.json`（`data/` 不入库）。

两批之间没有任何改动，召回区间却从 [15.1%, 15.7%] 变成 [13.2%, 20.1%] 且**重叠**。所以
「批内 0.6 个百分点」只是记录那一批的性质，不是误差上界；判断一个改动是否有效，仍然要求
两组分布不重叠，不能拿两个单点相减。完整对照与比较规则见
[eval-baselines.md](eval-baselines.md) 第六节。

复现：

```bash
export UV_CACHE_DIR=$PWD/.uv-cache
set -a; . /home/thin-time/repos/intelligent-diagnosis-rag/.env; set +a
uv run idr extract-eval --runs 3 \
  --out /home/thin-time/repos/intelligent-diagnosis-rag/data/output/reports/extract-eval-runs-3.json
```

报告 JSON 是 `schema_version: 2`：`run_details` 里是每次运行的逐篇明细、逐断言状态、多出的断言与命中集合，`distribution` 里是运行之间的两两重合度与召回/精度的分布。
